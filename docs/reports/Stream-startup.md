## Исправление

Перед CacheDataSink установлен ограниченный буфер256KiB. На каждую физическую
запись остаются свежие проверки mounted/writable/quota/free-reserve. Нет TTL
состояния карты и обхода квоты. Хвост сбрасывается с теми же проверками; после
частично неудачной записи данные не повторяются наclose. Delegate закрывается
и при ошибке, исходное исключение сохраняется. Формат кэша/ключи/URL policy,
приоритет/отмена/READY и версии Media3/yt-dlp не менялись.

PreparedApi показывает живые bytes/total/% общего кэша, даже когда фоновый
загрузчик уступает плееру. INFO меняется наCACHE при фактическом получении данных;
чтение статуса не меняет сохранённый план и не выставляет ложную READY.

## Дополнительные измерения и ограниченный план

После первой поправки v20 запрос API занял35.9s. Найдено повторное определение
носителей для каждой строки каталога. v21 использует один свежий read-only снимок
носителей на ответ; действия воспроизведения/записи продолжают проверять живое
состояние. Тест21готового файла подтверждает один опрос, read-only остаётся
доступным для просмотра, отключение отражается в следующем запросе без удаления.

Аппаратный результат v21 — PARTIAL/FAIL для плавного просмотра: десять снимков
за47–214s дали PLAYING лишь на части опросов, position311027→357701ms,
cache26738688→30932992bytes. API8.1–14.7s вместо35.9s, но это всё ещё медленно.
Сохранность данных/программы и продолжение просмотра PASS. Установка v20
завершилась, хотя ADB-клиент истёк по180s; версия и SHA установленного APK
проверены до восстановления. Последующие APK сначала передаются в собственный
/data/local/tmp, затем устанавливаются локально без очистки; свой APK-temp удаляется.

После двух ограниченных изменений причина оставшейся нагрузки уточнена read-only:
145cache-файлов; find1.36s, du1.5s. Полный quota scan делал canonicalPath для каждого
фрагмента, повторялся каждые250ms и отсчитывал интервал ДО самого долгого обхода.
То есть интервал успевал истечь во время сканирования.

Минимальные варианты: A) исправить обход и существующий общий ledger записей;
B) полная подготовка до просмотра; C) новый RAM/внутренний cache-tier (не реализован,
потребовал бы смены архитектуры). Выбран A, последняя ограниченная итерация v22.

NIO walk использует BasicFileAttributes и не следует symlink; исчезнувший при
очистке файл пропускается, остальные ошибки не игнорируются. Общий MediaBudget
считает все app-media записи под одним lock. Периодический пересчёт5s отсчитывается
ПОСЛЕ обхода, перед возможным превышением квоты принудительно сканируется снова.
Удаления до пересчёта могут только консервативно завышать учёт; read-only API
использует тот же ledger. Живой mounted/writable/free-reserve проверяется каждой
записью. Любая ошибка записи/доступности инвалидирует ledger, следующий проход
проверяет фактические файлы. Все production media writers используют этот gate;
неиспользуемый legacy helper не подключён к runtime.

Дополнительные тесты: долгий scan/окно после его завершения, общий лимит двух
писателей, force-scan после удаления, unchecked partial-write, карта отсутствовала
и вернулась с другими файлами. 386unit/lint/debug/release PASS. Если реальный
сквозной показ после v22 не проходит, фиксируется FAIL и оставшаяся причина,
без дальнейшего расширения архитектуры в этой задаче.


Ledger не кэширует доступность/запись носителя. Доступность проверяется каждой
записью, при её ошибке весь usage-cache инвалидируется (в том числе карта
отсутствовала и вернулась с изменёнными файлами). Период5s относится только к
пересчёту app-owned media: все их production writes уже проходят один общий
MediaBudget и учитываются инкрементально. При достижении лимита выполняется
принудительный обход, поэтому консервативный остаток после удаления не блокирует
освобождённое место. Свободное место Android/резерв проверяются живым statfs.
Тесты386PASS включают этот контракт. Собственный APK-temp на /data/local/tmp
не является медиафайлом пользователя и удаляется после подтверждения установки.

## Практический результат и оставшийся шаг

Три ограниченные поправки устранили измеренные лишние обращения к хранилищу,
сохранили квоты/проверки и исправили отображение прогресса. Полного исправления
прямого просмотра на этой H728 не подтверждено: функцию нельзя рекомендовать как
бесперебойный просмотр для детей. Надёжный доступный вариант — дождаться READY
в режиме полной подготовки, затем смотреть локальный файл.

Следующий минимальный шаг — отдельное измерение времени проверки носителя,
открытия/чтения блока и записи кэша при активном просмотре, чтобы локализовать
оставшуюся задержку. Новый cache-tier/изменение архитектуры не выполнялись;
после ограниченных неудачных циклов дальнейшее расширение в этой задаче остановлено.
Без Merge/Release/reboot и изменений Happ/HOME/системных настроек.
